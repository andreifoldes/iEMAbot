### 🚀 Added

- **One device per participant ID, in the Android app**: the Android app's background reminder poll, its notification receipts and its phone-sensing uploads now send the device token too, so a study set to **One device at a time per ID** covers them (from the app version that includes this; older installs stay unrestricted). On a device that does not hold the ID, the reminder poll stops quietly (nothing is cleared, and the app starts it again when opened), and phone-sensing batches already collected are kept on the device and sent once it holds the ID again (they are removed, as before, if the participant uses another ID on that device). Also: a participant who has left the study is now told so before the one-device check, so a device left behind still stops sensing and clears itself; and signing out stops the Android background work before it lets go of the ID.

- **One device or several per participant ID (app and editor)**: **Participants IDs** in the study editor has a new choice, **Devices per participant ID**: the same ID on any number of devices (the default) or **One device at a time per ID**. In such a study the app takes the ID for the device as soon as it is settled (link, typed, stored or made up) and sends a device token with every request about the participant. A second device is offered *Transfer to this device*; the first one is refused, keeps every waiting answer, voice memo and keystroke log (none of it counts toward giving up), pauses its queues, and is offered the same transfer. Signing out lets go of the ID. Replaces the old device lock, which called a service that was never part of this repository. Old versions of the app, and the Android app's reminder and sensing requests for now, are not restricted.

- **One device per participant ID (server side)**: a study can allow a participant ID on one device at a time (`pidDevices` "single"; the default "multi" changes nothing). The server keeps who holds each ID (`pid_lock.php`), refuses requests from another device with error 409 (an upload as a whole, never as a per-dataset error), and lets the person who holds the ID transfer it. Requests without a device token, from apps that do not send one yet, are not restricted. The app and the editor setting follow. Also fixed: `check_pid.php` now answers the Android app's cross-origin preflight, so the participant ID prompt works in the Android app.

- **Participant IDs page in the study editor** (new tile **Participant IDs**): choose whether anyone with an access key can join (random IDs, as before) or only participants whose IDs you list; with a list, choose whether the ID comes from the invite link or is typed. The list is entered by pasting, uploading a text or CSV file, or making random IDs, saved with its own button, and shown with who has joined and who has not. A CSV of personal links, one per listed ID, can be downloaded. `pidMode` and `pidFromUrl` are also settings in study specs for `create_study`.

- **Participant ID list in the app**: in a study restricted to a list, the app takes the ID from the link (unless the researcher turned that off), else the one the server accepted before, else asks the participant to type it. The server is asked first (`check_pid.php`), a refused ID leaves nothing stored or sent, an unreachable server is a retry rather than a way in, and a typed ID in another letter case becomes the listed spelling.

- **Participant ID list (server side)**: a study can be restricted to a list of participant ids (`pidMode` "list"). The list is stored separately from the study, uploads and the other participant requests refuse ids that are not on it (participants who already joined keep working), `check_pid.php` tells the app whether an id is allowed, Telegram invitations must name a listed id, and the admin features `GetAllowedPids` / `SetAllowedPids` read and replace the list. The study editor and the app's ID prompt follow.

- **A new self-hosted server starts with the demo study** (a short check-in, every question type and a test reminder; access key `demo`), so researchers have something to try at once, at `/pwa/?key=demo`. The installer adds it right after creating the first admin account (`cli/selfhost.php demo`, through the editor's own save), and prints its link. It is added only to a new server, so a demo study that was deleted does not come back when the installer runs again; `--no-demo` leaves it out. The image holds the study at `/opt/iemabot-demo/`.

- **Try it on your own computer**: *Getting started: for researchers* now explains how to install a copy on your own computer with Docker Desktop (`install.sh --domain localhost`) before asking IT for a server, what works there and what does not (phones, installing the app and reminders need the real server), and why a study needs a server rather than a computer left running.

- **Self-host kit** (`deploy/selfhost/`): a lab can run its own server with one command on a Linux VPS. The installer checks the machine, sets up HTTPS, creates the admin account before the server faces the internet, schedules nightly backups, and tests the result. `doctor.sh`, `update.sh`, `backup.sh` and `restore.sh` cover the rest, including running behind an existing web server and moving to a new server. Settings that depend on the server's address now follow from one value. See the *Self-host for your lab* guide.

- The image is published to the GitHub Container Registry for amd64 and arm64 with each release.

- **Create and check studies from the command line**: `study-cli/bin/create_study.php --spec=study.json` builds a study from a short JSON spec (title, access keys, languages, questionnaires with pages and questions of any type, optional schedule and settings), fills in everything the admin editor fills in when a researcher creates and saves a study (`id`, `serverVersion`, `packageVersion`, `lang`, the lists and objects the editor always writes, a questionnaire id each) and leaves out what still has its default, as the editor does. It refuses a spec with a list of all its problems (unknown fields or response types, wrong types, repeated or reserved question names, a choice question without choices, a check-in that points nowhere, an access key or id another study has) and then saves through the same `CreateStudy` / `SaveStudy` code as the editor. `--dry-run` stores nothing, and an option it does not know (a mistyped `--dry-run`) stops it before it does anything. `study-cli/bin/check_study.php --all` (or study ids, or `--file`) reads studies that already exist and reports what is wrong with them, for example a missing `packageVersion` (a warning: the admin editor repairs such a study each time it opens it), or an error such as a missing `serverVersion`; it changes nothing. Both are command-line tools; run them as the web user (`-u www-data`): `create_study.php` refuses to run as root, because the study's files would then belong to root. It is a separate module, the `study-cli/` folder (with its own tests, fixtures and README), that only calls the backend's public classes; the image holds it at `/var/www/html/study-cli`, so `docker exec -u www-data <container> php /var/www/html/study-cli/bin/create_study.php --spec=/tmp/study.json --dry-run` works. The scripts in `tools/live-study` can use its classes instead of building JSON by hand. The tests use the editor's real TypeScript classes (`npm run test:editor`): what the editor posts for a new study, and that it opens a stored study without repairing it, must equal what the factory makes. See *Backend > Create studies (CLI)* in the documentation.

- Web push: when a participant's study ends (their last check-in has closed or been completed), they get one **study complete** message under the study title, by default *The study has finished. Thank you for taking part!* It takes the place of the last reminder on the phone, so a reminder for a check-in that can no longer be done is not left there, and it is silent, as it can come at night when the last window closes. Sent once per participant, only when the study ended that day or the day before (participants whose study ended earlier get nothing), and only for schedules where every check-in has a last day or date or is answered once. Researchers can turn it off or change the text, per language, in the **Push notifications** panel (study JSON `studyEndNotificationEnabled`, `studyEndNotification`). It does not count as a reminder in the notification funnel.

- Participants who reached a study without notifications (declined the dialog, tapped *Not now* at onboarding, or blocked them later) are asked again **once a day**, in the web app and the Android app: a *Notifications are off* card above the questionnaire list. While the browser or Android can still show its permission dialog, *Turn on notifications* shows it; once it no longer does (blocked in the browser, declined twice on Android) the card explains how to allow them in the settings, and the Android app's *Open settings* goes straight to its notification settings. On an iPhone before the app is on the Home Screen it explains how to add it. Declining at onboarding counts as that day's ask and *Not now* hides the card until the next day; a participant who switched notifications off in Settings is never asked. On by default; researchers can turn it off under **Study settings → Participant permissions** (study JSON `notificationNudge`).

- **Daily check-in plan** (new **Edit study → Daily check-in plan** panel): an ordered list of check-ins per day, each with its own time range, prompted once (at the start of the range or at a random time inside it) and open for a response window. Response windows never overlap: by default a check-in is not prompted before the previous check-in's window has expired (or, as an option, the previous window closes when the next check-in is prompted), and each check-in can be completed once a day, so participants have at most one check-in open at a time. Each end of a range is a clock time, wake-up or bedtime plus an offset, or a split point of the waking day, which covers fixed windows (classic stratified random EMA), dynamic windows that follow each participant's day (e.g. wake-up to habitual bedtime split into four equal parts) and hybrids (e.g. "wake-up until 11:00", "19:00 until bedtime"). Any check-in, typically the evening one, can have its own response window. A range can end on the next day: at a clock time (e.g. 02:00 after midnight) or at the next morning's wake-up. Wake-up and going to bed are anchors with tiered fallbacks: an observed wearable event (Withings "out of bed" / "in bed"; for wake-up also the participant answering the first check-in), else tier 1 the participant's habitual time plus an offset, else tier 2 a fixed time. Answering the first check-in re-plans the rest of the day at once, also offline in the web and Android app. The same plan drives web push, Telegram and the Android app, which schedules the check-ins as local alarms (offline, on the minute; only a wearable-based wake-up comes through `api/native_pending.php`), and the participant app gates availability with the same calculation (new `api/daily_plan.php`, shared fixture `test/fixtures/channels/daily-plan.json`). Questionnaires in the plan are prompted by it only; their own schedules and sensor triggers are ignored. The notification preview in the Push panel includes the plan's prompts.

- Daily check-in plan: when a check-in can be answered and when it is prompted are now set separately. **Can be answered**: from the prompt for the response window (as before), or **throughout the range**, so a morning check-in can be open 06:00–10:00 whenever it is prompted. **Prompt**: at the start of the range, at a random time inside it, **when the participant gets up** (the wearable's out-of-bed event; without one by the usual wake-up plus a grace period, at that time), or **no prompt**. A check-in already answered is not prompted. A range can now start or end at the **usual wake-up + offset** (the participant's habitual wake-up time, else the plan's fixed wake-up), known before the participant gets up: −120 to +120 minutes is 06:00–10:00 with the default 08:00, and moves with each participant's habitual time. The habitual wake-up can differ at weekends: an optional second time item is used on Saturdays and Sundays (e.g. habitual wake-up time at weekends), with the weekday one as its fallback. A new **cool-down** keeps the next check-in closed for that many minutes after one is completed (and moves its prompt), so two check-ins are not answered in quick succession; a check-in whose window ends during the cool-down is missed. Works on web push, Telegram and the Android app, and offline in the app (shared fixture `test/fixtures/channels/daily-plan.json`).

- **One schedule for every study and channel** (new **Edit study → Schedule** panel, study JSON `schedule`): which questionnaires can be answered when, and when participants are prompted, now come from one place and one engine for web push, Telegram, the Android app and the app's own questionnaire list. Before, availability and notifications were worked out separately per channel (signal schedules, sensor triggers, completion filters and the daily check-in plan each had their own code, on the server and in the app), so a notification could arrive for a questionnaire the app showed as locked. Now one engine (`backend/schedule/Schedule.php` and its line-by-line port `web-pwa/src/lib/schedule.ts`, held together by the shared fixture `test/fixtures/channels/schedule.json`) turns the study's schedule and each participant's situation (enrolment, time zone, usual sleep times, wearable events, completions) into check-in windows; every channel only delivers what it says.
  - A schedule is a list of **check-ins**, each a questionnaire with: the days it runs on (from / until a day after enrolment, every N days, weekdays, day of month, dates); a daily range whose ends are a clock time, wake-up, the usual wake-up or bedtime plus an offset, or a split point of the waking day; a prompt (at the start, at a random time, when the participant gets up, **when a wearable reports an event** with a delay and a fixed or per-participant fallback time, or none); when it can be answered (from the prompt for a response window, throughout the range, or until the study day ends); how often (once per window, once per day, once in the study, or freely) and a minimum gap; whether it **starts by itself** in the app (e.g. at onboarding); and its notification (title, text, reminders, "Complete by"). Check-ins are open one at a time unless marked *open alongside the others*. The study's day start (e.g. 04:00), the wake-up and bedtime anchors and the cool-down are part of the schedule.
  - The habitual **bedtime** can differ at weekends: an optional second time item is used on Friday and Saturday nights, like the weekend wake-up on Saturday and Sunday mornings.
  - Questionnaires no longer have scheduling settings: the per-questionnaire *Filter and trigger* page and the trigger editor are gone, and the calendar is rebuilt on the schedule (below). A questionnaire without a check-in is never open.
  - **Existing studies are upgraded** when the server is updated to 3.7.0, after a backup of each study's config to `backups/schedule-upgrade/`: signal times, random signal times, fixed completion windows, wearable sensor triggers, active periods, completion filters, notification texts and the daily check-in plan become check-ins with the same timing; configs saved later in the old form (e.g. an imported file) are upgraded on save. A sensor trigger with more than one prompt a day now prompts once a day.
  - The server now knows every completed questionnaire (not just "something was uploaded"), so prompts and reminders stop for check-ins that are done on any channel. The app re-reads the participant's usual sleep times right after an upload, so new answers move that day's check-ins at once. The Android app plans all prompts on the device except those that depend on wearable events, which come from the server (`api/native_pending.php`); the app and the server always ship together. `api/daily_plan.php` is replaced by `api/schedule.php`.
  - For the SSRC study, `tools/live-study/set-ssrc-habitual-sleep-times.php` adds **Your usual sleep times** (wake-up on weekday mornings and at weekends, bedtime on weeknights and on Friday and Saturday nights), asked by itself at onboarding, and fits the four daily check-ins and their notifications to each participant's answers: the morning check-in when they get out of bed (Withings mat), else 30 minutes after their usual wake-up; the two daytime check-ins at random in the second and third quarter of their waking day; the evening check-in from 2 hours before their usual bedtime until an hour after it (08:00 and 23:00 until they have answered).

- **The Android app and the server always ship together.** Every deploy now builds the signed Android app from the same commit and the server serves it (`app/iemabot.apk`, described by the new `api/app_version.php`). The app checks on start and whenever it returns to the foreground: when the server has a newer build it shows *A new version of the app is available* with an **Update** button (opens the download; Android installs it over the current app and keeps its data) and posts one notification per new build. It never blocks: an older app keeps working until the participant updates. App version codes are now minutes since 1970 at build time, so every build installs over the previous ones. Apps installed before this change do not have the check yet: install the new build on those phones once.

- **Calendar** (new **Edit study → Calendar**), from the same schedule engine as availability and notifications. **Plan** shows the check-in windows, prompts and reminders of a sample participant who joins on a chosen day, with sample answers for the usual wake-up and bedtime (weekday and weekend), for the schedule as it is being edited. **Participants** lists every participant with their compliance so far (expected check-ins against completed ones, missed, last completion, time zone) and shows each participant's windows day by day in their own time, coloured completed, done elsewhere, missed, open or upcoming. Completions come from the study's response files, so the whole history counts. The web and Android app now send the device's time zone with every upload (the `timezone` and `timezoneOffset` columns of the response files), which the calendar uses; until a participant's next upload it falls back to their Telegram or push-subscription time zone.

- Participants' **Send error report** can also be filed as a GitHub issue (labelled `participant-report`), in addition to reaching the study's messages. Off until a repository and a fine-grained token with *Issues: Read and write* are set: on deploy from the `BUG_REPORT_GITHUB_TOKEN` secret (issues go to the deploying repository, or the one named by the `BUG_REPORT_REPO` variable), or on the server with `php cli/github_issues_setup.php set <owner/repo>`. Reports are queued and posted once a minute (`cli/github_issues_send.php`), at most 3 a day per participant and 30 a day per server; the issue holds the participant's note and the recent app errors with contact details and identifiers removed (emails, phone and other long numbers, IP addresses, URL query strings, tokens, @handles), plus the first half of the participant's user id, versions, and the browser and OS without the device model; the full user id, server address and study title are left out. Names written in the note cannot be recognised and stay in, so use a private repository.

- Tutorial: researchers choose which questionnaires the tutorial overview offers a practice run of (**Study description → Tutorial**, one checkbox per questionnaire, all ticked by default), e.g. to leave out a second daytime check-in identical to the first (questionnaire JSON `includeInTutorial`).

- Message pacing for every study and channel: when the participant app (web or Android) or the Telegram bot sends several messages in a row, such as the tutorial's "quick tour" and "What to expect", each one now waits behind a typing indicator until the previous one has had time to be read (at least 1.2 s, at most 10 s). The first reply to something the participant did is never delayed, buttons and question cards appear after the last message, and a returning participant reopening the app sees the opening messages at once. Researchers set the speed in the study settings under **Message pacing (words per minute)**: 238 by default, lower for more time, 0 to turn it off. Replaces the source-only `webPacedMessages` flag.

- Questionnaire items get an optional **Instruction** field (web/PWA app): a call to action shown on its own line after the item's explanation, in the regular text colour, e.g. "Count all times from when you first got out of bed…". Together with the existing **Explanation** field an item can read as question (bold), explanation (muted) and instruction. Item text written as plain text now keeps its paragraph breaks instead of running into one block. For the SSRC study, `tools/live-study/set-ssrc-nap-count-layout.php` splits the evening nap question into these three parts.

- Phone sensing in the Android app: in a study's new **Phone sensing** panel, researchers can collect the ambient light when each questionnaire is opened and submitted, Google activity recognition (still, walking, running, cycling, in a vehicle, recorded all day so the activity before, during and after every prompt is known), the raw accelerometer in a window around each prompt (minutes before and after and the sampling rate are configurable), and app usage by package name as daily summaries, raw events or both. Each can be turned on separately. Participants are asked for the Android permission a sensor needs when they enter the study and see what is collected under the new **Phone sensing** tile. The data uploads in the background to the new `api/phone_sensing.php` and is stored only in the main SQLite database (new `sensor_data` table, raw accelerometer as compressed chunks of about 4 bytes per sample in `sensor_chunks`, no CSV files); the `phone_sensing.zip` download is generated from there. Switching on the raw accelerometer shows a warning with an estimate of the data it will produce per prompt, per participant and day, and for the whole study. Not yet tested on real devices.

- Added option to specify y-axis minimum for charts.
- Added sensor-triggered prompts: in the trigger editor, an event trigger can fire when a Withings or Fitbit webhook reports new sleep, activity, weight, blood-pressure or ECG data, with an optional daily window, daily cap, delay and a time-of-day fallback. Needs the new `api/wearables_webhook.php` endpoint (see the Wearables docs). Not yet verified against live provider accounts. Fitbit's legacy Web API is scheduled to shut down on 2026-10-30; an experimental, untested placeholder for its successor, the Google Health API (webhook triggers only), is included; Google is not onboarding new projects, so it has never been run.

- Sensor-trigger fallbacks can follow each participant's routine: set *Fallback time from* to **Participant variable + offset** and name a time item (for example `habitual_wake_time` in an intake questionnaire); the fallback fires at that participant's latest answer plus the offset, and at the fixed time (**If the variable is not set, send at**) while they have not answered it.

- Participant app install flow, ported from the Sleep Diary prototype: the browser's install prompt is now captured before the app loads (so the **Install app** button reliably appears); iOS Safari and Chrome (v113+, iOS 16.4+) get matching Add to Home Screen steps and older iOS / Chrome / other iOS browsers get a clear update-or-switch alert instead of steps that can't work; links opened inside WhatsApp, Instagram, Mail and similar in-app browsers are steered to a real browser; desktop visitors can scan a QR code to continue on their phone; after installing, the app says to open it from the Home Screen (with a "can't see the app?" hint) and ticks off the funnel step; and iOS participants who arrived by invite link are shown their code to write down before installing.

- Smartphone-only studies: a new study setting, **Only allow participation on a smartphone (web)**, makes the participant app show an invite page on computers and tablets instead of starting the study: what to do, the invite code and participant ID to write down, a centred QR code you can tap to enlarge, other ways to open the link (copy it, or *I'm on my phone — continue here* on touch devices), and a browser tip. Off by default; a device that already consented is never turned away. The check runs before consent and before the participant ID is claimed, so scanning the code on a phone starts clean. The hosted study page uses the same layout.

- iOS participants can enrol with the details from their link: the installed app's code-entry screen now takes an optional **Participant ID** next to the invite code (iOS gives the home-screen app empty storage, so a personalised link's participant ID used to be lost), and the "Write these down" card shows both.

- Permission explanations during onboarding: before the browser (or Android) shows its own permission prompt, the participant app now says why the permission is needed, and the prompt only appears when the participant taps **Allow**. Studies with a voice-recording item get a new **Allow microphone access** step right after the notifications step (with guidance if access is blocked, and a way to carry on without); the Android app's notifications request now uses the same explain-then-ask card. When both are needed, the app says up front that it will ask for two permissions.

- Researchers can see and control these permissions under **Edit study → Study settings → Participant permissions (web)**: each permission shows which questionnaires or items need it and whether participants are asked during onboarding. Notifications use the existing web push switch (with a warning when scheduled questionnaires won't reach web participants); the microphone step is on by default for studies with a voice-recording item and can be turned off, in which case the browser asks the first time a participant records.

- **The participant calendar shows the notifications.** Under each window (Edit study → Calendar → Participants) every prompt and reminder is listed with when it was sent and whether the participant received and opened it (sent, delivered, opened, failed, or "No push logged"), coloured, with every step to the second on hover. Until now the calendar only showed when the notifications were planned. The push log does not say which notification an event belongs to, so events are matched to the planned times by time.

### ✏️ Changed

- **Practice runs draw the same 2 cognitive tasks as live runs.** A questionnaire page made up only of cognitive tasks (for example the four tasks of the SSRC check-ins) already showed 2 of them, drawn at random, in a real check-in, but a practice run showed all of them. A practice run now shows 2 as well, so the tutorial matches what participants will do.

- **Stronger protection for answers on the participant's device.** An answer is now saved before it is sent, so it survives the app being closed or the phone switching off mid-upload. Nothing is ever given up on: answers, voice memos and keystroke logs the server keeps refusing stay on the device and are tried once a day, where they used to be deleted after 20 refusals. If the device cannot store an answer, the participant is told and it stays safe while the app is open. Uploads are also retried every minute while the app is open, and time out instead of hanging. When the server stored an answer but its reply was lost, the app sends it again and the server recognises it, by the participant, questionnaire and moment it was answered, so it is stored once.

- **A server without `cron` got no nightly backup, and nothing said so.** Debian's Azure image is one. The installer now offers to install `cron`, and `doctor.sh` warns while no nightly backup is scheduled.

- **Planning a check-in now offers to replace the always-open one.** A study's first questionnaire starts open at any time, so that it works straight away. That check-in used to stay after a researcher planned their own, so participants could still answer whenever they liked.

- **Participants' answers were lost when they arrived within a second of the previous upload**, for example right after a cognitive task: the server refused them and the app, which did not read that part of the reply, took them for sent. It now sends them again after a moment. The queue of unsent answers is also worked through one item at a time and saved after each, so that nothing queued in the meantime gets overwritten and nothing is sent twice.

- **A free-text question made in the dashboard did not show in the participant app**, because free text is the default type and defaults are left out of the saved study. A questionnaire of only such questions appeared empty.

- A new study's first questionnaire is now open by default. Before, participants of a study without a check-in were told there was nothing to answer, and nothing warned the researcher. **Publication, Links & QR code** now warns about any questionnaire that no check-in opens.

- **Publication, Links & QR code** now offers the **Link for participants** first, also as the QR code. Before, the page only offered links to the older study page and, on servers that are not in web-only mode, to install instructions for another project's app. The self-host kit installs in web-only mode.

- The demo study now holds every question type.

- Telegram is now fully optional: without a bot set up on the server, researchers see no Telegram panel, switch or compatibility icons, and the background jobs do nothing (no log lines, no files in the data folder). It appears as soon as a bot is added under **Server settings → Messaging channels**.

- Participant app (web and Android): the app no longer asks participants for a name, in any study. Participants are identified only by their participant ID (assigned automatically or taken from the invite link), the Details panel no longer shows a username, and a name stored by an earlier version is removed from the device on the next launch. The **Do not ask participants for a name (web)** study setting (`webSkipName`) is gone, as it is now always the case.

- SSRC study: the two daytime check-ins are now titled **📋 Daytime Check-in 1** and **📋 Daytime Check-in 2**, matching ☀️ Morning and 🌙 Evening (`tools/live-study/set-ssrc-daytime-emoji.php`).

- Participant app (web and Android): a check-in is no longer lost when the app is closed or the phone kills it in the background. The answers are saved on the phone after every step, and reopening the app carries on at the question it stopped on, with the earlier answers shown again, as long as the check-in's window is still open. Once the window has closed the saved answers are dropped, so they never carry into a later check-in. A check-in parked with **Remind me later** waits on the list instead of reopening by itself, and it is now also dropped when its window closes (before, it was offered again in the next day's window). Resuming keeps the order of randomized pages, so it no longer jumps to a different question. In the web app, an app update arriving during a check-in no longer reloads the page mid-answer: it applies the next time the app goes to the background.

- Fixed: in the web app, a returning participant without notifications could have their schedule restarted on their first visit after joining, so the app said the study had not started yet. The questionnaire list was worked out before the app knew which participant it was.

- Fixed (again): scrolling past the end of the conversation still scrolled the whole participant app on the screen with questionnaires that are not open yet: the header slid away and the chat row (menu, input, send button) rose off the bottom of the screen over empty space. - **Security hardening: study content can no longer run script.** Question text, descriptions, post-study notes, chart descriptions, publication titles and researcher messages are HTML written in the editor and shown to other accounts and to participants. They are now passed through an allowlist (DOMPurify, pinned) before they are shown, in the admin interface and in the participant app, so a study can no longer carry script, event handlers, `javascript:` links, forms or styling that takes over the screen. What the editor produces (text formatting, headings, lists, links, images, text alignment) is unchanged. Links from untrusted data (publication links, web-access entries) are only followed when they are http(s) or mailto.
- **Security hardening** (from an IT security audit):
  - The start page (`index.php`) no longer builds JavaScript from the address (`key`, `from_url`), which allowed script injection; every value is now encoded and `from_url` must be a base64 string.
  - `lang` (address, cookie or update request) can only be a plain language code, so it can no longer be used to read other files on the server, such as other studies' configs. The same goes for the fallback server address (`fromUrl`) and the login token id in the `tokenId` cookie, which could be used to read or delete files outside the token folder (log-out was reachable without logging in).
  - `GetFullStudy` (the full study config, including its access keys) now requires a role in that study (read, write, message or reward) or server admin; before, any logged-in account could request any study.
  - Login cookies (`account`, `tokenId`, `token`) are now `HttpOnly`, all cookies are `Secure` over HTTPS, and the PHP session cookie is `HttpOnly` and `SameSite=Strict`.
  - `api/admin.php` rejects requests that a browser marks as coming from another site (`Sec-Fetch-Site` / `Origin`), as protection against cross-site request forgery. Scripts and tools that send neither header (curl, Playwright's API client) are not affected.
- **Security hardening: server-rendered pages, push subscriptions, uploaded media, reset device.**
  - The no-JS questionnaire and the no-JS study overview / install pages escape what a participant typed (it is shown again when a page is redrawn) and pass study text through the same allowlist as the admin interface and the app (`HtmlSanitizer`). Before, a crafted form post could run script on the server's origin.
  - Web-push subscriptions are only accepted for the browser vendors' push services (Google, Mozilla, Apple, Microsoft) and only for studies that exist; the same check runs before every send. Before, the server would send requests to any address a subscription named.
  - Uploaded recordings, photos and keystroke logs are only served as audio, video or image types (never as a page, never SVG), with `nosniff` and a policy that blocks scripts.
  - *Sign out and reset device* in the app now also deletes voice recordings and keystroke logs that were still waiting to upload.
- Participant app: before today's wake-up is known, check-ins timed from it say when they open if the participant gets up at their usual time, instead of all showing "Opens after you get up" (for a check-in prompted at a random time: "Opens between 11:45 and 15:30 if you get up at 08:00"). Getting up earlier only moves them earlier.
- **Error reports on GitHub are only filed in a private repository.** The server now asks GitHub whether the repository is private before it posts anything (every run that has something to send), and the setup command refuses and switches the relay off for a public one. When reports are passed on, the app's *Send error report* dialog says so: *your description and these technical details may also be passed on, without your name or contact details, to the developers of the app on GitHub*.
- **Wearable tokens and chat ids are never stored in plaintext.** Without the encryption key (`wearables_token_key`, created by `cli/wearables_setup.php` when a provider is set up) a token is no longer written at all; older plaintext files are encrypted the next time they are read. A participant who tries to connect a wearable on a server without the key gets "Wearables are not set up on this server" before being sent to the provider. Handoff links are not accepted on a server without a key (their signature would otherwise be a plain hash anyone can compute). `cli/wearables_setup.php genkey` no longer replaces an existing key by accident (that made every stored token unreadable): it needs `--rotate`.
- **Android app: an invitation link no longer switches the study server by itself.** A `esmira://join` link (QR code or web link) names the server that receives the participant's answers and recordings. The app now asks first, showing the server name (*Connect this app to the study server …?*, or *change your study server from … to …?* when one is already set), and does nothing if the participant says no. A link that names a remote server over plain `http://` is ignored (only `https://`, or this machine for development). The *new app version* download must come from the server the app talks to: an address on another site in the server's answer is ignored.
- **Invite link generator: random participant IDs by default.** `invite-generator.html` made sequential IDs (`P001`, `P002`, …), which are easy to guess; a participant ID is what identifies a participant to the server. It now defaults to random IDs (12 characters from a 32-letter alphabet, 60 bits, from the browser's crypto generator, kept stable until *New random IDs* is pressed). Sequential and custom lists still work, with a warning that such IDs can be guessed.
- **Study data downloads as CSV or Excel, built from the database.** The data list now offers *CSV* and *XLSX* for each questionnaire, the event log and the web-access log. Both are read from the SQLite store (the response header `X-Export-Source: sqlite` says so) and never fall back to the CSV file: if the database is missing a row the file has (compared by row identity, so a file that holds the same row twice is fine) or fails, the download stops with an error instead of handing over a different dataset. The file is built completely before the first byte is sent, so a failure never leaves a cut-off download, and a `"` inside a cell is doubled. Text cells that start with `=`, `+`, `-`, `@`, tab or carriage return are prefixed with `'` in the CSV so a spreadsheet cannot run a participant's answer as a formula (plain numbers such as `-3.5` are left alone); in the XLSX every text answer is stored as text, so it cannot be a formula at all. The download works after the CSV file has been removed. Dated copies keep their plain link.
- **New command to delete the old CSV files after the move to the database.** `cli/purge_legacy_csv.php` (a dry run unless `--apply`) removes response CSV files that have not changed for at least 7 days. It refuses unless CSV writing is switched off (`write_csv_files` is `false`), the live database holds everything the files hold, and a separate database backup (`--backup=`) opens read-only, passes the integrity check and holds it too. Nothing calls it automatically, and until `write_csv_files` exists it always refuses.
- **Build supply chain pinned.** The server image no longer resolves anything new at build time: the PHP packages come from a committed `composer.lock` (`composer install`, not `composer update`), the base image, the Composer image and the Dockerfile frontend are pinned by tag and digest, and `install-php-extensions` is a fixed release whose checksum is verified. The accessibility tool installs from its own lockfile without install scripts, and the deploy workflow packs the build context before that install runs. Android signing keys are only handed to release builds, which run in the `android-signing` GitHub environment (the owner limits it to `main`: `website/docs/deployment/android-signing.md`); pull requests and debug runs never reference them. CI also checks that `composer.lock` matches `composer.json`.
- **Security headers on every response.** The server now sends `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and `frame-ancestors 'self'` (other sites can no longer put the admin pages or the participant app in a frame; the Telegram Mini App page `handoff.html` also allows Telegram's own web client). A `Content-Security-Policy-Report-Only` policy is added as well: browsers log what it would block but block nothing yet. The image enables Apache's `mod_headers` for this (it also makes the existing no-cache rule for the app's service worker take effect). The start page no longer uses an inline `onload` handler; the app reads its start values from a `data-esmira-init` attribute, so the page behaves as before. HSTS is not set in the image; the reverse proxy must send it (see the "Security headers" documentation page).
- **Security hardening: smaller items.**
  - Secrets (login tokens, study access keys, fallback-server tokens) are compared in constant time, so how long a check takes no longer says how much of a guess was right. A study access key must now match exactly: two keys that merely look like the same number in scientific notation (such as `1e3` and `1000`) are no longer treated as equal.
  - The server's own data files are only read back as the objects each file is meant to hold (`unserialize()` with an allowed-class list); a tampered file can no longer make the server create other objects.
  - New study and questionnaire ids, and the login delay, come from the system's secure random generator. The id ranges are unchanged.
  - Files and folders that hold credentials (the server config with its API keys, account password hashes, login tokens, wearable tokens and connection state, fallback tokens, chat-channel bindings and invites) are readable by the web server's user only. Existing files are tightened the next time they are written, and when the container starts. The Data and privacy page of the docs lists which files.
  - Participant app: the window that runs a cognitive task can no longer navigate the app away, open popups, or show dialogs (`sandbox="allow-scripts allow-same-origin"`), and the offline task route in the service worker only serves files under `/webapp/` (before, it fetched any path on the server for any page of the app). A task hosted somewhere else on the same server loads from the network as before, without an offline copy.
